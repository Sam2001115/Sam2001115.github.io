01. Objective

Develop a high-fidelity hardware simulator in C++ that replicates the behaviour of an OUSB (Open USB) board — a physical AVR-based development board used in university coursework. The goal was to create a fully functional software environment where digital logic and register-level manipulations could be tested and validated without requiring the physical hardware.

03. The Challenges

Challenge 1 — Register-Level Emulation: The AVR architecture manipulates hardware at the bit level — individual pins are set or cleared by masking specific bits within 8-bit port registers. Replicating this in software meant every instruction had to manipulate virtual registers in the exact sequence and precedence the real hardware would follow.

Challenge 2 — Error Precedence: In a real hardware environment, certain errors — such as invalid port access, out-of-range values, or malformed instructions — must be caught and reported in a strict order of priority. Reporting errors in the wrong order would cause the simulator to provide false data or crash rather than fail safely. Implementing this required a carefully ordered validation engine that ran before any instruction was executed.

Challenge 3 — File I/O Command Execution: The simulator needed to accept a plain text file containing a sequence of hardware instructions and execute them in real-time — translating human-readable command strings into register manipulations and outputting the resulting virtual hardware state.

04. The Solutions

Register Emulation — C++ Classes + Bitwise Ops: Each hardware port (Port B, Port D, etc.) was represented as a C++ class containing an 8-bit virtual register. Individual pin states were controlled using bitwise OR to set bits and bitwise AND with NOT-mask to clear them — directly mirroring the way AVR hardware operates.

// Virtual register pin control — mirrors AVR hardware behaviour void setPin(uint8_t &port, uint8_t mask, bool state) { if (state) port |= mask; // Set bit — HIGH else port &= ~mask; // Clear bit — LOW } // Read individual pin state from virtual register bool readPin(uint8_t port, uint8_t mask) { return (port & mask) != 0; }

Error Precedence — Validation Engine: A structured validation engine runs before any instruction is executed. It checks — in priority order — for syntax errors, invalid port references, out-of-range pin numbers, and data type mismatches. If any check fails, execution halts and the correct error code is reported according to the hardware specification. This ensures the simulator follows strict Fail-Safe protocols at all times.

File I/O — Custom Command Parser: A custom parser reads the instruction file line-by-line, tokenises each command string, maps tokens to internal port/pin operations, and updates the virtual registers accordingly. After each instruction executes, the simulator outputs the current state of all virtual LEDs and switches to the console — providing a clear, visual representation of the virtual hardware state at every step.

// Simplified parser + console feedback loop while (getline(inputFile, line)) { auto tokens = tokenise(line); // 1. 06. Lessons Learned

Abstraction Enables Hardware Emulation

Representing each hardware port as a C++ class with an 8-bit internal register made the simulation both accurate and extensible. Good abstraction meant adding new ports or pin behaviours required minimal changes to the core logic.

Error Ordering Is Part of the Specification

In embedded systems, the order in which errors are detected and reported is not a minor detail — it is part of the hardware contract. Implementing the validation engine in strict priority order was essential to matching real hardware behaviour exactly.

Bitwise Operations Are the Language of Hardware

Every pin state change in AVR comes down to bit masking. Writing this in C++ reinforced how closely low-level programming maps to physical circuit behaviour — and why understanding bitwise logic is fundamental to embedded systems work.

Simulators Are Powerful Debugging Tools

Being able to test complex instruction sequences in software — without needing the physical board — dramatically accelerated debugging. Building the simulator deepened the understanding of the hardware it was emulating far more than just using the board would have.
